# OpenCode 外部执行代理插件：实施方案

日期：2026-09-07。本文保留规划阶段的目标和边界；后续已按用户授权开发并安装插件，当前交付与剩余事项见 [开发验收记录](2026-09-07-opencode-worker-plugin-development-acceptance.md)。

## 1. 已确认的目标

用户继续与 Codex 主代理沟通。Codex 理解需求、拆分适合委派的任务，通过独立 Codex 插件调用本机 OpenCode，使用已有 OpenCode Go 订阅的 `opencode-go/muse-spark-1.3-contributor`，回收成果并验收；需要返工时续接同一 OpenCode 会话。

规划阶段，用户已选择 Contributor 并授权临时测试，当时不安装插件、不修改现有路由 Skill 或全局配置。随后用户明确授权按此方案开发和验收，执行结果以开发验收记录为准。真实项目代码没有作为测试输入外发；后续 GitHub 源码更新按用户另行授权执行。

新插件独立维护执行能力；当前 GitHub 工作流仅增加可选执行通道。主代理判断和最终验收保留。插件不会自动变成 Codex 原生 `spawn_agent` 角色，也不会自动出现在其原生子代理树。

## 2. 建议架构

```text
用户 → Codex 主代理
          │ 现有路由 Skill：是否委派、任务范围、执行者选择、验收
          ▼
     opencode-worker 插件（拟定名称）
          │ 本地 STDIO MCP：status / start / wait / followup / cancel
          ▼
     插件管理的本机 OpenCode Server
          │ 独立任务会话、明确工作目录、显式权限
          ▼
     OpenCode Go → Muse Spark 1.3 Contributor
          │ 文件、工具结果、消息和状态
          └─────────────────→ Codex 检查和交付
```

采用 OpenCode 原生 Server API 管理会话。CLI `run --format json` 保留为诊断入口，不同时维护两套生产执行后端。Server 的异步提交、消息查询和 abort 已适合上述五个工具，避免自行拼接模型协议。

首版默认一个执行任务。并发、队列、Web 管理界面、通用多 Provider 路由、OpenAI Responses 转换代理均不属于首版。Go 认证由现有 OpenCode 管理，插件不读取或复制密钥。

插件管理独立服务，不接管用户日常 TUI 服务、不停止其他 OpenCode 进程。服务只监听 loopback，正式实现使用随机可用端口和本机认证；服务日志不能混入 MCP stdout。请求本机服务时明确绕过 HTTP 代理。只有首次需要调用时才启动，不因每次健康检查发起模型请求。

## 3. 插件与 Skill 的职责

| 组件 | 负责 | 边界 |
|---|---|---|
| 工作流 Skill | 任务是否适合委派、选择 Muse/Luna/主代理、任务交接、结果验收 | 不保存端口、进程路径、模型 API 协议或认证 |
| 插件 MCP | 运行时发现、执行、状态、续接、取消、产物定位 | 不擅自拆任务、换模型、扩大权限或发布成果 |
| 插件内简短 Skill | 如何调用本插件、理解状态和失败、Contributor 的数据条件 | 不重复维护完整总调度规则 |
| OpenCode / OMO | 模型调用及具体工具执行 | 使用外部执行任务的明确权限；不继承 Codex 权限的假设 |
| Codex 主代理 | 决策、冲突处理、验收、最终答复 | 不与运行中的执行任务重叠修改同一文件 |

OMO 不等于单个模型。首版保留本机 OMO 加载，运行一个实际发现的主角色，但禁止该任务继续委派。完整 OMO 多代理编排不是首版验收条件。如以后开放，必须额外解决所有子会话的完成判定与递归取消。

角色名从 `/agent` 发现，不把配置键 `sisyphus` 当作运行时角色名。本轮实际发现 `Sisyphus - ultraworker`。若升级后无法确定已选择的角色，返回配置问题，禁止静默回退到默认角色。主模型显式锁定 Go Contributor；不回退到 Zen 免费通道或其他付费 Provider。辅助模型和 OMO 路由也需核对，不能仅凭主模型名称宣称所有调用使用相同额度。

## 4. 拟议工具契约

工具名称为设计草案，尚不可调用。

| 工具 | 输入 | 返回与行为 |
|---|---|---|
| `status` | 可选 `task_id` | 无 ID：依赖和服务状态、目标模型、实际角色、最近验证时间；有 ID：任务状态、结果与产物位置 |
| `start` | `request_id`、工作目录、任务正文、只读/写入模式、允许写入范围、允许命令 | 持久记录任务后提交，及时返回 `task_id`；不阻塞到整个任务完成 |
| `wait` | `task_id`、等待上限（最多 30 秒） | 返回新进度或终态；等待超时只表示仍在运行 |
| `followup` | `task_id`、`request_id`、追加任务 | 同一会话新一轮；首版仅在上一轮终止且状态已核实后接受，不自动扩大原权限 |
| `cancel` | `task_id` | 请求 abort，核实停止并返回已产生的修改；不自动回滚 |

任务交接沿用现有 Skill：目标、已有结论、相关文件、允许修改范围、验收方法、需要返回主代理的决策、用户授权边界。小任务不要求额外生成庞大任务文档。

`request_id` 用于避免 Codex 在提交响应丢失后重试而启动两次写任务。只需本地记录与查重，不做通用消息队列。提交是否发生不确定时返回 `unknown`，先对账，不盲目重跑。

每项任务保存最少必要信息：任务/会话 ID、工作目录、原始交接、实际 Provider/模型/角色、权限、轮次消息标识、起止时间、工具错误、最终消息、产物/变更位置。状态使用本地 JSON 原子替换即可，不新增数据库。持久状态放用户数据目录，不能写入会升级替换的插件缓存目录。

不保存或向主代理倾倒完整推理文本。只回传摘要、可定位的工具结果与产物；未知成本或额度表示为 unavailable，不能表示为零。

## 5. 状态与成功判定

任务状态：`submitted`、`running`、`needs_attention`、`completed`、`failed`、`cancelled`、`unknown`。其中 `completed` 仅代表执行轮次结束，不代表主代理验收通过。验收状态单独表示为 `pending / accepted / changes_requested`，由 Codex 决定。

必须处理以下真实差异：

- HTTP 204 是提交确认，不是完成。
- 异步提交后，短时间可能仍查询到 idle。本轮已有 idle → busy → idle 观察。因此要结合该轮新消息 ID、assistant 完成标记和错误，不能看到 idle 就结束。
- CLI 退出码 0 不能证明任务成功。本轮工具写入被拒绝，但 CLI 正常退出，末尾 `step_finish.reason=stop`。
- 一次 tool-calls 的 step_finish 不是整个任务完成。
- 工具曾失败但随后修复，保留错误供验收；不能仅因历史错误永久判失败，也不能忽略最终未解决的错误。
- 超时与断连不能证明执行已经停止。要查询原会话，再决定取消或继续等待。
- 本轮在提交后立即 abort 返回 true，1 秒后会话仍进入 busy；等待 busy 后 abort 则返回 idle 和 MessageAbortedError。插件应先记录取消意图，检查该轮是否真正开始，对后到的执行再次 abort 并核实终止；在此之前保持取消处理中，不允许新写任务接手。
- 插件进程重启后，先根据记录重新查询原服务/会话；无法确定时保留 unknown，不把任务标成成功或自动重启写入。

## 6. 可用性与自动路由

“插件已安装”“工具在当前任务可调用”“OpenCode 环境就绪”“最近一次模型请求成功”分别表示，不能合并成一个永远有效的 ready。

当工作适合委派、外发在授权内、当前能发现插件工具，且 `status` 返回所需运行时能力时，Skill 可选择 Muse 通道。首次安装或关键配置变化后，用一次受限实测建立最近成功记录。正常任务不重复空跑模型。

本轮已授权使用 Contributor 测试；以后按用户对项目和外部执行的既有授权工作，不把安装插件当作所有项目的外发许可，也不每次重复确认已有许可。

用户明确要求某模型时尊重选择。未明确指定时，Muse 可作为满足条件的外部执行候选，Luna 保留其现有启用/禁用状态；初版不依据一次接入测试宣称 Muse 普遍优于 Luna。架构、开放式根因判断及难以独立验收的工作仍留给主代理。

插件未安装或不可用：保留原工作流。任务已经开始或可能改过文件：先确认停止并回收修改，再决定主代理接手或其他执行者接手。配额耗尽或认证失败不触发无限重试，不自动切换到其他计费通道。

## 7. 文件与权限

测试临时目录、Git worktree 都不是安全沙箱。插件不能宣称自动继承了 Codex 的文件系统与审批限制；需要向 OpenCode 明确传递任务权限，并验证其实际效果。

首版只支持主代理明确交给插件的工作目录。写入任务以独立、已准备好的 worktree/临时副本为推荐路径；Codex 负责准备正确的源状态和后续整合。插件不偷偷从默认分支创建一个遗漏未提交修改的工作副本，也不自动 commit、merge 或覆盖主目录。

同一文件一次只有一个写入者。已有脏文件不能被清理或回滚。任务终止后用基线与实际差异检查范围，包含新建文件。提示词限制和事后 diff 不能替代执行中的权限控制。

本轮绝对路径和相对 directory 的窄路径规则曾失败；会话级 `**/allowed.txt` 许可与默认拒绝的组合，随后通过允许文件写入、禁止文件拒绝的正反测试。`/path` 的 worktree 为 `/`，工具标题呈现 `private/tmp/.../allowed.txt`，与按 worktree 相对路径匹配的解释一致，但没有完成源码层根因证明。正式实现从运行时取得 directory/worktree，生成准确路径规则，在 Git worktree 中验证；不要把宽泛文件名通配符或 edit 全允许直接作为正式范围控制。

运行 shell 可以执行代码并绕过仅针对 edit 工具的路径限制。允许命令必须是任务明确需要的，遇到超范围权限返回 needs_attention；不得默认加 `--auto` 或广泛允许 shell。需要不可信代码的强隔离时，使用实际系统沙箱/容器；首版不声称提供这类隔离。

## 8. 源码与改动范围

建议独立项目名 `opencode-worker`。本轮只在当前工作流仓库保存方案和测试记录，不创建或发布新仓库。

最小插件结构：

```text
opencode-worker/
  .codex-plugin/plugin.json
  .mcp.json
  skills/opencode-worker/SKILL.md
  src/                 # MCP 与 OpenCode 会话管理；按实际需要拆文件
  tests/               # 契约测试和显式启用的真实接入测试
  README.md
```

建议 TypeScript + 官方 MCP SDK；OpenCode HTTP 接口优先使用运行时 fetch，不额外引入通用 HTTP 框架。实现前核对目标主机 Node 路径和插件运行环境；不能依赖当前交互终端 PATH 恰好生效。采用插件官方脚手架和校验器，安装走个人 marketplace，不复用 Luna 安装器写插件配置。

现有 `codex-workflow` 后续只改：

1. `skills/sol-worker-routing/SKILL.md`：增加可选 Muse 通道、发现与状态规则、回收失败任务；保留现有任务交接、所有权和验收原则。
2. `AGENTS.md` 与 Skill 中禁止 bridge 的条款：增加用户授权的独立 OpenCode 插件范围，继续禁止复活旧 DeepSeek 原生角色/协议绕过。不泛化删除原约束。
3. `scripts/install.sh`：仅在发布新版 Skill 时更新已知旧 Skill 摘要识别，避免正常升级被判为未知内容；不扩展安装器管理目标。
4. README、变更记录、版本：随实际交付更新。若 Personalization 的旧措辞阻止新通道，提出精准替换文本；不自动修改 App 设置。

工作流 Skill 与插件不硬性绑定安装。插件可以独立被用户手动调用；缺少插件时工作流仍能使用原有执行者。接口发生破坏性变化时再做版本兼容检查，不预先设计多版本适配体系。

## 9. 实施顺序与验收

| 阶段 | 交付 | 验收 |
|---|---|---|
| A：本轮 | 方案、受限本机测试记录 | 清楚区分运行事实、未验证项与建议 |
| B：插件最小闭环 | 打包、发现、服务启动、start/status/wait | Codex 真正通过插件工具执行一个只读任务，确认 Provider/模型/角色及结果 |
| C：写入和生命周期 | 权限、续接、取消、状态持久化 | 允许/拒绝路径、固定命令、真实修改与独立测试、同会话返工、busy 取消、断连恢复、不重复启动 |
| D：工作流接入 | Skill 的可选通道及文档 | 有插件按规则分派；无插件保留原行为；Luna 状态不变；显式禁止外发/委派仍生效 |
| E：个人安装验收 | 校验并安装插件，在新 Codex 任务中发现工具 | 真实 MCP 调用闭环通过，随后才称插件可用；发布与 Git 外部操作需另行授权 |

测试优先覆盖可达风险：退出码 0 的失败、idle 的提交竞态、角色回退、取消未停止、重试造成重复写入。本轮已观察到实际 Go 上游限流并恢复，应将 OpenCode retry 状态映射为仍在运行且附上重试原因；计入任务预算，插件不再叠加无界重试。额度耗尽和认证失败可通过合成 API 响应测状态处理，不为制造这些错误消耗真实额度或改用户认证。

接入验证不替代模型能力比较。路由优先级以后可用同一源状态、同一任务与独立验收比较一次通过率、总耗时及返工量；不必在插件开发前建设基准平台。
